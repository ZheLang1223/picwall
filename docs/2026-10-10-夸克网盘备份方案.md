# 夸克网盘承载 Picwall 异地备份方案

> [!summary] 结论
> 本地 13G 中 picwall 占 12.6G：pics/（活数据）6.1G 不能动，真正的浪费点是 backups/ 里的
> 内容寻址 blob 库 6.1G——它是 pics 的完整镜像，而 `make offsite`（NAS+加密）从未实际跑过，
> 等于备份只有本机一份。夸克网盘（已授权，剩余约 480G）正好接管 blob 库：备份格式升级为
> 「db 快照+清单留本地、媒体 blob 直传夸克」，恢复路径改为从夸克按 hash 拉取。
>
> **实施范围（2026-10-10 修订）**：本期只做 §3 备份 v2；本地 blobs 的清理（--prune-local）
> 改为**手动显式步骤**，跑不跑、何时跑由用户决定。§6（原图上云、本地只留缩略图、按需回源）
> 因依赖「删除本地原图」而整体延后，仅作为后续可选形态保留。

## 1. 现状盘点（2026-10-10 实测）

| 位置 | 大小 | 内容 | 判定 |
|---|---|---|---|
| `data/pics/` | 6.1G | 内容寻址原图+缩略图，应用实时读 | **活数据，不动** |
| `data/backups/` | 6.1G | `blobs/`（全量媒体镜像）+ 7 份滚动 db 快照与 manifest | **迁移目标** |
| `data/export/` | 480M | 保留帖归档（pics 的第二份副本，设备同步源） | 可选迁移 |
| 其余（somedia/weibo-archive 等） | <0.4G | — | 不值得迁移 |

夸克侧：账号已授权（折浪，超级会员），容量 6.19T/6.67T，剩余约 480G；目录
`来自：ClaudeCode/Somedia备份` 已建好（fid `92ea87e389864bd585c9e88153e59e89`）。

## 2. 为什么备份 blob 库是浪费点

`app/backup.py` 的 create() 每轮把 pics/export 全部文件硬链进 staging，逐个算 sha256 后
复制进 `backups/blobs/`（内容寻址去重）；manifest 记 hash 清单；restore() 用
blobs + manifest 重建整库。设计上有两个后果：

1. **blobs 永不清理**（滚动只裁 `.snapshot` 和 `.db`），所以它单调增长到与 pics 等身——
   本地永远躺着两份全量媒体。
2. **直接删本地 blobs 不可行**：下一轮 create() 发现 blob 缺失会原样重灌 6.1G，
   空间立刻回弹；而 blobs 又是本地恢复的唯一数据源。

所以「省空间」的正确形态不是删文件，而是**把 blob 库的家搬到夸克**。

## 3. 方案：备份格式 v2（远端 blob 库）

### 3.1 create() 改造

- db 快照、cookie/x_auth 凭据快照、manifest 仍留本地（合计几 MB）。
- 媒体文件：算 sha256 后**不再复制进本地 blobs/**，改为确保该 hash 的 blob 已存在于夸克
  `Somedia备份/blobs/`（内容寻址天然去重，每轮只传新图）；manifest 增加
  `blob_store: "quark"` 标记与远端路径约定。
- 保留现有完整性门禁：integrity_check、decisions_sha256、preexisting_missing 一律不变；
  新增 `remote_missing`（本轮上传失败的文件数），非零时备份仍成立但 `make status` 显黄。

### 3.2 restore() 改造

- 校验逻辑不变（size + sha256 逐文件验）；blob 来源从「本地 blobs/ 目录」改为
  「本地命中用本地，缺失按 hash 从夸克下载到临时目录→校验→落盘」。
- 整库恢复 = 下载 6.1G，按 hash 命名所以可断点续传、可并发。

### 3.3 迁移与兼容

1. 首传：现有 `backups/blobs/` 6769 个文件一次性推夸克（CLI 支持断点续传），
   完成后本地 blobs **原样保留**——期间 restore 仍走本地，零风险回退。
2. create()/restore() 切换远端模式单独一个提交，随时可 revert。
3. `data/backups/` 里旧 `.snapshot`/`.db` 滚动策略不变。
4. **本地 blobs 清理（--prune-local）是手动步骤**（2026-10-10 修订）：核对
   全量清单 ⊆ cloud_blobs 且抽样校验通过后，由用户显式执行才删除，届时本地再省 6.1G；
   不执行则本地行为与今天完全一致，只是多了云端副本。

### 3.4 make 集成与运维

- `make backup` 不变名不变参（内部走 v2）；AGENTS.md「日常操作只记 make」不破坏。
- `make status` 体检增加一行：云端最新快照时间 + remote_missing 计数。
- 定时：服务内 04:10 purge 之外，backup 保持现有节奏；上传失败重试交给 CLI 断点续传。
- 夸克 CLI 调用约定：本机环境下必须带渠道标记运行
  （`CLAUDECODE=1 CLAUDE_CODE_ENTRYPOINT=cli node ~/.zcode/skills/quarkclouddrive/scripts/quark-drive.cjs …`，
  ZCode 终端不带该标记会被服务端以「无法识别 Agent 环境」拒绝，错误码 -104）；
  skill 升级走 `bash scripts/install.sh`，授权码 `login --token` 模式。

### 3.5 风险与对策

| 风险 | 对策 |
|---|---|
| 夸克不可达时备份退化 | manifest 记 remote_missing，`make status` 显黄；本地行为不阻塞 |
| 恢复依赖网络与第三方 | blobs 观察期回退窗口；夸克账号本身是 SVIP（到期 2027-03），`make status` 提示续费 |
| 首传 6769 文件触发限速 | CLI 自带断点续传；首传放夜间跑，分批校对 |
| 隐私 | 备份内容是用户自有微博图与个人批注；**凭据文件（cookie.txt / x_auth.txt）自 2026-10-11 起不进 blob 库、不上云**（见 manifest 的 `local_only`，只随本地快照 `local/` 子目录留存），历史快照经查也未上传过凭据。现有 `make offsite`（NAS+AES）路径原样保留，夸克是其补充而非替代——两者可并存 |

## 4. export/ 处置（可选，480M）

上传 `data/export/` 到 `Somedia备份/export/` 后，本地副本是否删除取决于手机端查看习惯：
夸克 App 可直接浏览，但「保留视图打包下载」「相册同步」走的是本地目录。建议先传不删，
用一两周确认夸克端体验后再定。

## 5. 不做的事

- pics/ 活数据不上云：应用实时读图，网络盘当活库既慢又危险（断网=相册全灰）。
- 「缩略图本地留、原图夸克按需取」属于 picwall 媒体层改造（媒体读取路径要加回源逻辑），
  量级远超备份模块，需要时另立任务。
- library/、门户语料不过夸克：体积小且受 TCC/构建链路约束，动了没收益。

## 6. 延伸形态：原图上云、本地只留缩略图（2026-10-10 可行性评估）

> **状态：延后**（2026-10-10 决策）——整节依赖「删除本地原图」这一前提，用户已明确
> 暂不考虑删原图，故本节仅作可行性存档；何时重启，以下评估与实施顺序仍然有效。

「看大图时才从网盘取，本地不存原图」技术可行，且与本案的云端 blob 库是同一条路走到底。
实测数据支撑：pics/ 里**原图 5.8G / 3517 张，缩略图+头像仅 336M**——墙卡与详情页浏览
只吃缩略图，真正需要原图的只有 大图查看、下载、批量打包 三处。

### 6.1 架构

服务端代理回源，浏览器永远只认识 `/media/...`：

- `/media/{path}` 是唯一的媒体出口（server.py，内容寻址、immutable 长缓存），
  回源逻辑只改这一处：本地命中照旧秒回；未命中 → 按 hash 查 `cloud_media(file→fid)` 表
  → 从夸克下载流式回给浏览器，同时写入一个**有上限的 LRU 缓存目录**（如 2G，
  超限逐出最久未读）。「本地不存」的严格形态是零缓存，但那样同一张图看两次下两次，
  纯浪费流量；2G 缓存 = 最近看过的秒开，总量可控。
- 采集管线改「传完即删」：入库仍先落本地原图（保入库可靠性），上传夸克拿到 fid 记表后
  删本地原图、保留缩略图；上传失败走既有 image_jobs 式重试队列自愈。
- 存量迁移：3517 张原图全量推夸克（断点续传、分批限速）→ 逐个 sha1 校验 → 删本地。
  工具脚本模式照抄 tools/regen_thumbs.py。

### 6.2 收益

本地媒体从 6.1G 降到 **~0.4G（缩略图）+ ≤2G 缓存**；叠加本案备份 v2（blob 库上云），
工作区 13G → **约 2-3G**。且备份与在线看图共享同一份云端副本，不用存两份。

### 6.3 代价与边界

- 大图**首开**多 1-3 秒 WAN 延迟（灯箱本就有 loading 态）；墙卡滚动、详情页不受影响。
- 断网或夸克授权过期 → 大图/下载不可用，墙照常浏览（降级需明确提示，不静默白屏）。
- 隐私换体验：能在线看 = 云端是**明文**原图（加密包无法流式回源）。与本案备份的
  加密选项互斥，二者只能选一——选在线看，就得接受明文存自己账号的网盘。
- purge（3 天清理）要联动云 GC，否则网盘侧孤儿只增不减；批量 zip 走回源路径，
  大包导出变慢。
- Quark 开放接口有限速与配额，回源要排队+重试；CLI 子进程方式每次调用约 1s 开销，
  够用但天花板明显，量大了换 Python 直连开放平台 API（客户端可替换设计）。

### 6.4 实施顺序（每步独立可回退）

1. 本案备份 v2：原图全量镜像上云（本地暂不删）——这是本形态的前提。
2. `/media` 回源 + fid 表 + LRU 缓存。
3. 存量迁移脚本：上传→校验→删本地原图。
4. 采集管线「传完即删」；purge 云 GC、zip 回源、export 复核收尾。

挂载网盘当本地盘（同步盘在线模式）看起来零改造，但不取：Quark macOS 端在线模式
支持不明、FUSE 挂载上跑 HTTP 服务随机读不可控，且 pics/ 缩略图与原图混居必须先拆目录——
绕一圈还是回到服务端代理，可靠性却差一个量级。

## 7. 实施记录（2026-10-11 00:15）

备份 v2 已按 §3 上线，范围与 §3.3 修订一致（删原图形态 §6 延后未做）：

- `app/cloud.py`：BlobStore 双实现。QuarkBlobs 经 quarkclouddrive skill CLI
  （需 `CLAUDECODE=1` 渠道标记；回读实际用 `download` 命令——1.0.24 CLI 尚无文档所写的
  `read-file` 子命令）；LocalBlobs 与历史行为逐位一致，默认模式即它。
- db v8 `cloud_blobs` 登记表；`backup.create/restore` 面向 store，restore 改流式
  取 blob，失败清场，全有或全无语义经测试固化。
- `tools/backup_to_quark.py`：首传/续传/抽样回验/prune；`make picwall-cloud` 入口。
- 实测：6768 个 blob（约 6.1G）25 分钟首传；中途一批 200 个失败，重跑幂等续传补齐；
  抽样 50 个回读 sha256 全部一致后执行 prune，本地 blobs 目录已删——`data/` 13G→6.6G，
  `backups/` 只剩 db 快照与 manifest（5.2M）。quark 模式 `backup.create()` 全程 15 秒，
  新增 blob 直传云端不再落本地。
- 体检：`make status` 与 `/api/status` 的 `cloud` 字段（登记数 / 最新 manifest 覆盖率
  covered / 实际后端 store）。`make backup` 已切 `PICWALL_BLOB_STORE=quark`。
- 恢复路径：宿主终端 `PICWALL_BLOB_STORE=quark PICWALL_DATA_DIR=… .venv/bin/python
  tools/restore.py`（不带参数 = 最新快照恢复到临时目录演练后自动清理；`--batch <快照>
  --target <空目录>` = 定点恢复，按 fid 从夸克回源，逐文件 sha256 校验）；
  整库约 6.1G 下载量。
