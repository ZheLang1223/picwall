# PR 汇报：好例子与反面例子

来源：[@Fei2411 在 X 上的“GPT 与 Gemini 的真实测试#1”](https://x.com/Fei2411/status/2123354076771692631)（2026-11-19）。
作者用同一份 AGENTS.md 规则（即本仓库 [AGENTS.md](../../AGENTS.md) 的“汇报 PR”一节）、
同一句提示词“现在有哪些pr”，对比了 Gemini 4 Neon 与 GPT 6.2 Sol。

## 好例子：Gemini 4 Neon

作者评价：“这是我见过最干净的汇报……分点清晰，内容概括的好，信息简洁同时非常准确完善，状态和结论也很准确。”

从截图整理出它的做法：

- **先给总数和分类**：一句话说清开放 PR 总数，以及“自有 / 合作者 / 外部”各多少、其中几个是草稿，并附一份可搜索的完整清单。
- **每类一段摘要**：
  - 自有：哪些是新开、CI 在等结果；哪些已推补修、待独立复审（CI 几绿几红几等待）；哪些建议关闭、哪些留作下个版本候选。
  - 合作者：点出“方向待定”的几个，并列出涉及的主题。
  - 外部：说明已核对开放状态，逐项改动见清单，并**如实写明“CI 本次未核对”**。
- **明细用表格**，每行一个 PR，列为：PR 号 / 是什么（附 `Refs #Issue`）/ 状态（合并与 CI）/ 独立 review 状态与结论。
  结论用固定词：未审（今日新开）、初审“需改”且已改完待复审、已审 → **需你拍板**（并给出理由和 review 记录文件）。
- 关键结论加粗，不确定或没核对的地方直说，不编造。

## 反面例子：GPT 6.2 Sol

同样的规则和提示词，跑了约 5 分钟，“几乎一点信息都没给”。作者认为它是第一个**完全无视 AGENTS.md 规则**的模型：
没有分类、没有逐个 PR 的状态和结论，汇报不能用。

## 给代理的要点

- 先读本仓库的 AGENTS.md 再汇报，严格按三类和固定的分级用词来写。
- 外部 PR 必须读过代码再评；没读、没核对的地方明说，不要猜。
- 宁可给一张信息完整的表，也不要一句空泛的概述。
