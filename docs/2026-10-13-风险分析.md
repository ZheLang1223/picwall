## 3. 本轮新发现与处置

### F14 🟡 备份搭车补只挂在 `make start`，日常最常用的 `make picwall` 不触发；失败静默

`auto-maint` 的超 24h 补备份只被 `make start` 尾调；`make picwall`（改代码/.env 后的日常重建入口）
不经过它——实测：容器 21 分钟前被拉起，最新快照仍是 41 小时前。且 auto-maint 的备份以
`$(MAKE) backup >/dev/null && echo 完成` 收尾，失败时无任何输出（静默吞掉，最坏情况用户以为有备份）。
单机常驻不重启的场景下，RPO 退化为「距上次手动 make start」。

**处置（本轮已修）**：`picwall` 目标健康检查通过后尾调 `auto-maint`（同一超 24h 门禁，新鲜时零开销）；
auto-maint 备份失败改为显式提示「单独跑 make backup 看完整输出」。

### F15 🟡 异地副本落后最新快照（covered=False）

最新快照 `picwall-20261012-043113` 由 local 模式真实备份产出：manifest 记 6763 个非凭据文件，
`cloud_blobs` 登记的 6768 个 key 覆盖不了其中 5 个新 blob → `/api/status` `cloud.covered=False`，
`make status` 显示「make picwall-cloud 续传」。夸克上的异地副本停在上上轮快照。

**处置**：不代跑（外部写操作，走用户夸克账号）——下次 `make backup`（quark 模式搭车补）会自然补齐；
或手动 `make picwall-cloud --verify-sample 50 --prune-local` 立即续传并回收本地 6.1G blob。

### F16 🟡 磁盘回落黄区

上轮清理后 18G → 今日 10–11 GB（95% 用量，`make status` 黄）。备份 staging、恢复演练、抓取落盘
同一前提。清理对象（Time Machine 本地快照、缓存等）属用户资产，不自动动；体检行已常驻。

### F17 ⚪ X 采集通道 url 无服务端 scheme 校验（已补）

浏览器代抓 `POST /api/ingest/x` 的 `url` 字段原样入库；前端有 `safeUrl()` 只放行 http(s)
（`app.js:929`），但服务端 normalize 层无同款校验——纵深只有一层。**本轮补刀**：
`sources/x.py::normalize_tweet` 对非 http(s) 的 url 回落到站内规范地址，+1 契约测试。

### F18 ⚪ LocalOwner 特权完全依赖宿主端口映射的正确性

本机入口 = 免配对管理员。容器内两个监听器都绑 0.0.0.0，把 8081 隔在回环后的是 compose 的
`127.0.0.1:8081:8082` 映射——若日后改映射丢掉 `127.0.0.1` 前缀，局域网内任何设备即得管理员入口。
compose 注释与 README 已写明，此处提升为显式风险条目：**改 compose 时该前缀不可动**。

### F19 ⚪ demo.clear() 删文件不走引用计数

演示清理对 pics 行直接 unlink，绕过 purge 的引用计数保护。演示图由本地生成、内容寻址名与抓取内容
撞 sha1 概率可忽略，实际风险≈0，记录为边界不修。

### F20 ⚪ restore 产物统一 0600、属主=执行恢复的用户

macOS Docker Desktop/OrbStack 共享层按宿主用户放行，容器（uid 1000）读写正常（上轮已实测）；
若未来迁 Linux 宿主，宿主/容器 uid 错位会使恢复产物容器不可读。平台边界，迁移时须重验。

### F21 ⚪ 容量边界的两个常量

夸克 blob 无 GC（CLI 无删除能力，云端只增不减，SVIP 2027-03 到期）；`repair_local` 每 24h 对全部
pics 逐文件 sha256（当前 1183 帖/17G 无碍，量级上来后是与备份同级的 I/O 峰值；容量基准沿用
2026-10-02 数据设计审查 §5 的实测口径，原文已退役）。
